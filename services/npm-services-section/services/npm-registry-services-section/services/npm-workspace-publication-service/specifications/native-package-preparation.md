## Architectural choice

Keep the existing private runSourceWorkerProcess, original bounded synchronous
executor and original PNPM metadata/precall/observation services. Add only named
fixed lock-preparation and separately admitted frozen-receiving operations at the
composing owner. Do not route these through publish-package's full install/build
preamble, destructive node_modules replacement or standing-cache fallback.
Ordinary build callers, package-manager command derivation and issued dependency
pins stay unchanged. PNPM-specific grammar/policy remains in PNPM's typed APIs.

The worker composes original source-qualified roles; their exact source/module/
package/import identities are explicit, not claimed to be installed releases.
The actual original native launch and its shebang/Node/ps execution closure must
be received, not inferred from the metadata operation's different Node-prefixed
launch. Shared custody code may be factored privately only if unchanged metadata
and build behavior is independently regressed; no parallel controller.

  not produced by stripping an inherited environment after refusal.

  custody reads. No caller program/argv/module/callback authority.
- Named operation picks only an original PNPM-derived command. A child creates
  the real process-local precall capability and asserts that exact request before
  invoking the original executor. Parent owns the exclusive intent boundary.
- Separate finite native/outer deadline and output thresholds for lock/frozen;
  metadata45s/1MiB is not asserted sufficient. Record raw overshoot/ENOBUFS before
  any stricter receiver refuses. Fresh resource/inode/time admission belongs to
  the caller and must cover archive/store/materialization effects if selected.

  and await owned-group quiescence even after direct child exit. Final parent

  No crash recovery, escaped-group cleanup or unknown-scope signalling promised.
- Failure consumes the attempt and preserves original raw terminal/evidence,
  native lock/history/cache/store changes. No silent rollback, cache fallback or
  automatic retry. Replay requires a genuinely separately admitted new operation.

## Selected API/lifetime refinement

Add a fixed source-qualified preparation factory at this original owner, sharing
its private supervisor and custody machinery rather than duplicating a runner.
Its parent-side operation lifetime is one explicit source/cache context:

1. `refresh` receives canonical inputs, fixed bindings, inherited transport and
   the derived cache allocation, and returns retained public evidence plus an
   opaque process-local prepared-lock ticket only after real lock execution and
   whole-group receiving. The PNPM capability is held privately by this parent.
2. `materialize` consumes that ticket plus separately admitted full-content stage
   inputs/bounds; execute the existing frozen install with ignore-scripts and the
   separately named PNPM prepared-online vector. Its sole additional option is
   `--config.update-notifier=false`, suppressing the optional pnpm@latest query
   which is outside this exact content operation. Ordinary callers stay unchanged.
   It is an online content/store/materialization operation, not an automatic
   fallback. Its existing command has no NDJSON reporter: receive successful
   frozen execution, unchanged source/history, group settlement and actual
   installed-member comparison, not an unobserved fresh policy verdict. Return
   a process-local installed ticket only after those original observations.
3. `materializeOffline` is an explicitly selected alternative to `materialize`,
   with exactly the same complete archive/content/capacity admission. It uses only
   the native content store; independently held archives are NOT store entries.
   A missing store archive refuses with retained native evidence. It never falls
   back to online acquisition and consumes the original prepared ticket.
4. `verifyOffline` consumes the installed ticket and uses PNPM's separately named
   prepared offline frozen vector. This adds the native-supported
   `--no-optimistic-repeat-install` to the unchanged legacy offline vector, so an
   unchanged-workspace early return cannot masquerade as a verifier event. It
   does not force installation or fresh policy computation. Actual original
   verifier events remain required. Its cached outcome is explicitly non-fresh and
   must satisfy the narrow PNPM same-path/stat/history causal profile. This check
   of an existing received installation is not called a new clean installation.
   It re-admits the complete held content/capacity and repeats selected installed
   archive/member receiving after execution, because offline work can relink.

The API has no arbitrary command/program dispatch. Only original source-bound
package-manager/PNPM APIs choose commands. The original parent capabilities are

Lost process-local tickets do not imply a durable resume or permit JSON replays.
