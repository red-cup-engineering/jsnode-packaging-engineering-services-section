# Intentional pin-set consumer receiving

The original `publish-package --pin NAME@VERSION ... --pin-only --apply` operation owns intentional changes to a consumer's already declared exact dependencies. The continuing [Group enterprise Work](https://github.com/561-group/internal-services-section/blob/main/lib/agency/works/serving-always-on-agents.json) requires this same producer to make coordinated supplier adoption efficient while retaining its native policy and receiving.

## Required behavior

Treat the complete authorized pin set as one source transition. Validate every name, exact version, dependency class and conflicting duplicate before writing any consumer input or invoking its package manager. A rejected entry leaves the original manifest, lock and policy unchanged. Preserve all unrelated declarations and peer changes.

Apply the admitted set to the original consumer manifest once, then use the existing native package-manager lock/install operation once for that complete set. Keep the current protected-input custody, registry and artifact identity, dependency-age policy, genuine section-owned receipt, source qualification and receiving mechanisms. Use the existing fallback only for its currently qualified failure class; an input-custody refusal retains its original outcome. Run the consumer's original receiving once after that final coherent graph is installed.

The original receipt names the whole intended set, source input identity, native refresh disposition, generated lock identity and actual consumer outcome. A failed installation or receiving retains the real source state and original effect correlation for continuation.

## Demonstrated operating cost

On October26 the current original CLI loops over pins, and each `applyDependencyPin` performs a complete graph refresh. The Console's four coordinated pins and FeltOS's two pins therefore multiplied the same native installation labor. FeltOS's CSE restoration alone ran20:34:27–20:50:25 and returned the same six refused consumer cases; the executing FeltOS and CIE importers were subsequently observed to resolve the same actual CSE0.1.15 provider. Retain these facts as the improvement demand. An exact dependency pin is not complete behavioral compatibility.

## Native derivation and receiving

Derive this bounded change at the original publisher's existing `publishPackageGate`, `applyDependencyPin` and `refreshConsumerInstall` ownership. Reuse native command planning and protected-input receiving.

Receive a multi-pin case by observing one final manifest transition, one native lock/install and one original consumer receiving, with every admitted pin represented in its real receipt. Receive invalid or contradictory entries before any write or native invocation. Receive installation failure, protected-policy mutation, concurrent source change, unrelated-field preservation and original fallback correlation through the same existing owner. A supplied single pin retains the same resulting behavior. Source construction, qualified carrier publication and installed consumer adoption retain their original distinct receiving.
