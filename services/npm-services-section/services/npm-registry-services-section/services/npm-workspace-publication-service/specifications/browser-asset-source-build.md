# Frozen browser asset source qualification

## Receiving requirement and owner

Durante and Ruinfold already build their browser programs with
`@red-cup-engineering/project-browser-asset-tree-service@0.4.2`. A landed-package
publisher must include the generated `dist` tree in the archive. Source-only
packing cannot satisfy a package whose browser server needs that tree.

Code owns build admission, native installation, test evidence and generated
product custody. The existing GitHub publisher retains authenticated source
acquisition and fixed-artifact publication. This refinement adds a recipe to
`./source-build-qualification` and the original `publish-package --qualify-build`
worker. It does not add a publisher, runner identity, deployment target or lock
refresh operation.

## Admitted source

The manifest declares exactly `node scripts/build-browser-assets.mjs`, the
runtime asset-tree provider at `0.4.2`, exact registry dependency selectors and
`dist` in its publication files. An optional `prepack` is exactly `npm run build`.
The native Node test command has confined test globs; balanced quotes around a
single glob preserve its identity without admitting shell commands. No build
prefix is admitted in this browser recipe's test command.

The committed adapter is the existing literal seven-line module that imports
`fileURLToPath` and `buildCloudflareStaticAssetTree`, derives the owner root from
`../`, exports `buildAssets` and calls it only when invoked as the program.
Only the JSON array of additional assets varies. It contains at most 64 unique
confined paths to authored regular files. Additional statements, dynamic options
or an alternate root/output path refuse before native work.

`web/index.html`, the adapter and a PNPM v9-format lock must be authored regular
files. The bounded native lock form has the standard settings/importers/packages/
snapshots sections and inline SHA-512 registry-integrity resolutions. Explicit
tarball URLs, local/git bindings, aliases, escaped key spellings and alternate
top-level composition forms refuse before installation. Only native plain or
single-quoted scalar keys, block package entries, known package metadata fields
and native snapshot/list forms are admitted. Tagged/complex keys and flow package
entries refuse even when another entry supplies a legitimate integrity; uppercase
and protocol-relative tarball locators cannot acquire an alternate spelling.
Deprecation prose URLs
remain prose. This guard does not interpret a dependency graph; native PNPM owns
the complete lock parser and frozen manifest-consistency check.
The project npm configuration, if present, selects only the supplied
canonical registry. The optional workspace policy is the existing list of exact
release-age exceptions. Competing locks, manager hooks, dependency overrides,
workspace membership and redirected source refuse. An existing `dist` tree
refuses before the provider can replace it.

## Native transition and custody

1. Receive exact authored source bytes, executable modes and unredirected paths.
2. Run the original fresh-install operation with the owner's PNPM manager,
   `--frozen-lockfile`, explicit `--ignore-scripts`, isolated HOME/configuration
   and implicit lifecycles disabled. An npm environment alias alone does not
   establish PNPM's native lifecycle policy.
   PNPM owns full lock parsing/resolution. The original installation custodian
   preserves manifest, lock, registry and workspace bytes and absence.
3. Receive the adapter and lock again, then receive the actual importer-relative
   provider name/version and entrypoint. Execute the fixed native Node argv for
   the admitted adapter. Preserve its provider identity in the build evidence.
4. Receive original build freshness and required passing native test evidence.
5. Receive all authored inputs unchanged and all new regular products confined
   to `dist`. Receive each declared web product, every normalized local module
   reference in generated HTML and each extra asset with its original bytes.
6. Bind generated bytes and modes to the original in-process qualification.
   Only `receiveQualifiedPublicationBuildProducts` can subsequently supply those
   products for packing; a serialized report grants no product authority.

The public receiver requires steps 1 and 2 only, exact source version, PNPM
`verify` mode and the same adapter/lock/policy evidence. Failed tests, empty tests,
missing products, source mutation or a changed supplier cannot qualify a carrier.
No publication, version selection, consumer repin or host activation occurs here.

## Acceptance and limits

Component cases cover Durante-style extra assets, Ruinfold's quoted recursive
test glob, adapter/configuration refusal before work, frozen-install identity,
incomplete output, authored-source preservation and post-receipt mutation.
Native consumer qualification must separately execute both unchanged game source
candidates through this original worker and receive every generated product in
the packed archive. Actual registry publication and host receiving remain later
claims at their existing owners.

Code's current main manifest also declares PNPM service `0.1.0-dev.192` absent
from its committed lock. This unrelated discrepancy must not be hidden by
refreshing that lock as part of a browser recipe test. Scoped qualification may
use a separately recorded exact-manifest composition; it must not claim a whole
checkout frozen installation.
