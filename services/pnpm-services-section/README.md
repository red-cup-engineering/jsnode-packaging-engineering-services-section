## Requirements and responsibility

The accepted bounded policy permits a fresh first-party artifact only when its
exact source revision, packed integrity, declared dependency closure, meaningful
test evidence and independently authorized receiving can all be established.
Namespace membership, version freshness, a successful merge, an opaque evidence
string, a caller's `approved` field and review prose do not establish eligibility.
GitHub `COMMENTED` is not automatically rejection or approval: the existing
source receiver makes the judgment under the applicable integration rule.

This component is evidence-comparison machinery, not the Group ownership
authority. Before enabling it, the composing owner must establish that the
immutable repository ID and package-to-source mapping belong to the existing
Group-owned source index. Authenticated receiving of an external or client
repository does not suffice. A namespace string, caller flag, or generic allowed
repository list is not that ownership proof. This production binding remains
unimplemented and must be exercised before any effective first-party exemption.

PNPM owns eligibility and native policy projection. The original npm publication
owner owns pinned source/artifact production, verification results, lock creation
and frozen installation. The existing GitHub owner owns authenticated source
receiving and durable receiving receipts. This section never publishes, installs,
opens credentials, changes clocks, changes a threshold or writes a consumer lock.
Ordinary dependencies, including unqualified first-party dependencies, remain
subject to the consumer's unchanged age rule.

## Architecture and detailed design

The original publisher retains an immutable verification result from real
bounded command execution over exact source and artifact bytes. Each result
binds source repository/revision/directory, artifact identity and SHA512,
declared closure, command enrollment, full process outcome and retained output
digests. Required suites must run and their required cases must pass; optional
skips require an explicit source-owned enrollment. Timeout, signal, failed
start, truncated output, empty execution and uncovered required cases refuse.
Only safe synthetic fixtures and an explicit environment may feed retained
qualification output; secrets and private client material are not qualification
fixtures.

The existing source receiver independently receives that immutable result and
the exact source through authenticated invocation context. Its original receipt
custody supplies the decision, principal and evidence references. A new decision
may qualify an already published artifact; it must not manufacture a historical
source-receiving receipt for its earlier GitHub merge. Historical artifact source
must remain readable after branch movement, so exact immutable source receiving
must not silently substitute the current branch head.

The PNPM predicate compares those retained identities and evidence. The public
policy function is a deterministic transformation, not an authority boundary:
production callers must resolve receipts through original owner custody, not
deserialize caller assertions and label them trusted. The original publisher
must perform that binding before invoking the predicate. No JSON-only public
entrypoint may turn an arbitrary receipt into an effective age exemption.

Native exclusion selection is exact `name@version`, but PNPM's match does not
bind integrity. Therefore original receiving also verifies every selected native
lock entry's origin/integrity against the qualified artifact closure before
frozen installation, and checks lock, manifest and effective policy afterward.
Conflicting duplicate selections, aliases, a changed lock or a changed policy
refuse. Unqualified transitive entries are not promoted by a qualified parent.
For a changed manifest the original lock writer resolves with lifecycle scripts
disabled, validates the resulting lock, then uses the original frozen receiver.

## Opt-in original-native installation observation

### Owning requirements and limits

PNPM Engineering owns the public `./native-observation` service, its private
preload, exact native-provider qualification, endpoint classification and native
event interpretation. The publication receiver owns process execution, resource
admission, termination, frozen-input checks, installation replacement and durable
receipts. This service does not install, fetch, terminate, alter policy or replace
transport. Native NDJSON alone cannot distinguish a pending archive request from
an overlapping strict-policy metadata wait. The qualified provider's original
Undici diagnostic channels add bounded request facts without replacing its
original dispatcher. There is no newly introduced transport or controller.

The initial source contract supports Node 24.19.0 with the original PNPM 11.28.5
distribution SHA256
`e3738fda08262f74611d7a1ffc11b3e87fa52b466c07eb73211d179ebcb98810`.
A changed provider needs source qualification; a version string alone does not
admit it. The service receives an explicit Node program and unmodified PNPM entry
arguments, checks the original package/bin/distribution and executes a separate
unobserved version probe. It binds its own manifest and two-module, Node-builtin-
only service/preload closure. Source digests bind received bytes, not independent
institutional authority. Source, issued package and installed consumer remain
separate evidence.

`createNativeObservationService()` returns the frozen typed service
`pnpm.native-installation-observation.service.v1`, with `prepare`, `revalidate`
and `receive`. `prepare({program, arguments, cwd, request})` admits an own-data
request containing an existing real `receiptDirectory`, selected `targets` and
optional integer `maximumEvents`/`maximumBytes`. Each target contains exact
`name`, `version`, `registry` and `tarball`. Endpoints must be same-origin HTTPS,
with no embedded credentials, query or fragment. This selects observations; it
does not authorize a request, redirect or changed registry. One explicitly
source-qualified fixture factory option, `qualificationRoot`, permits only
127.0.0.1 HTTP within a real owned fixture working directory. It is not exposed
as production JSON or a release-age exception.

Budgets default to 4,096 events and 1 MiB, with finite domains 1..16,384 events
and 4,096..8,388,608 bytes. Unknown fields, getters, symbols, sparse selections,
invalid exact versions and invalid finite budgets are refused before provider
execution. These limits separately bound the private transport stream and the
safe native-event projection, not total installation memory or disk. Receipt
serialization, duplicated safe logs and fixed source/provider metadata add
bounded overhead; the original process's 32 MiB stream cap remains unchanged.
The config is at most 2 MiB. There is no unlimited fallback or unbounded request
history. A bounded request correlation map never implies completion on eviction
or loss.

The returned opaque session is meaningful only to that service instance;
serialized or copied tickets cannot supply evidence. The command delta is exactly
one private `--import` prefix, the original `--reporter=ndjson` projection and one
child-local config-path environment entry. The publisher must still qualify the
unmodified base provider and compare identities. The service does not return an
alternate executable. No global agent, NODE_OPTIONS, policy, retry, auth, registry
or package-manager configuration is changed. Version probes do not participate in
the install observation session.

The inherited preload exits before any validation or I/O when `isMainThread` is
false. PNPM worker threads inherit Node arguments; they must not open the same
session file or emit duplicate startup/final markers. This deliberately observes
only the original direct-child main-process Undici context, not every thread or
transport. A private expected parent-PID/entry binding is checked before opening
the event stream, so inherited forks cannot claim that session either. This is
context exclusion, not fork coverage or descendant process supervision. Node
24.19 documents the inherited preload behavior at
https://nodejs.org/download/release/v24.19.0/docs/api/cli.html#importmodule .
The original-PNPM synthetic fixture must prove the relevant archive and metadata
requests actually occur in that context before the observation is used to explain
a real consumer wait.

### Evidence meaning and privacy

Only selected package/version and endpoint category, bounded correlation ID,
relative monotonic time, response status and an allowlisted error code leave the
preload. Raw URLs, paths, queries, headers, bodies, credentials, error messages
and arbitrary native records never enter phase events. Private owner-selected
configuration and source-custody identities remain separate from phase output.
The consumer projects only native `pnpm:lockfile-verification` started/done/failed/
cached and selected `pnpm:progress` fetched/found_in_store events. Native imported
paths are not guessed into package identities. Other native records are discarded
and counted; raw stdout/stderr are represented by byte counts and SHA256, not
persisted as diagnostic plaintext.

Request creation means only that the native request object was created. Headers
are not archive body completion; trailers are not store commit. Native
fetched/found_in_store means the native fetching promise resolved. Metadata can
serve resolution as well as strict-policy verification. Report overlapping
observed pending scopes without claiming a unique network or policy cause.
Even a natural final marker yields an observed prefix, never complete coverage of
all native work or an installer verdict. Malformed/truncated records, out-of-order
correlation, missing startup/final markers, exceeded budgets and reader/write loss
remain partial/unknown. Callback exceptions are contained and cannot throw into
PNPM. Reader loss does not change native exit status. Hard termination may leave
only a prefix and must be reconciled by the original process owner; no exit hook
or cleanup guarantee is invented.

### Qualification and source-to-issued migration

The public-export unit suite is included in `files` and `receivingTests`.
`test/native-observation-native.test.mjs` is a separately configured real native
assay. It requires `QUALIFIED_PNPM_ENTRY` and `PUBLICATION_RECEIVER_MODULE`, and can
retain fixtures in an existing `NATIVE_PHASE_FIXTURE_ROOT`. No supplied variables
means skip, not native qualification. It uses a loopback-only controlled fixture,
original frozen lock/policy, original PNPM, original publisher receiver and
source-composed service. It must distinguish archive-before-headers and
strict-policy-metadata stalls, preserve successful installation despite bounded
observer loss, and prove main-thread-only worker inheritance. It never receives a
production consumer or requests a public registry.

The declared development version is not an issued release. Source-only direct-JS
composition binds this actual module/export/closure and the publisher candidate;
it must not rewrite a consumer manifest or lock to a fictional issued pin. The
existing source-binding mechanism may compose a qualified temporary source
closure, restoring its bindings and prohibiting install lifecycles while active.
After separately authorized actual issuance through the original landing
publisher, receiving must inspect the archive/public export and exact transitive
closure, pin the verified issued dependency at the original consumer and rerun
that consumer's tests. Until then no production JSON observer selection is
implemented or admitted. No Work/Procedure allocation is inferred from these
local source and synthetic test receipts.

Provider, supplier and private configuration bytes are revalidated inside the
publisher's exclusive execution path after memory admission, immediately before
invocation. Revalidation compares all prepared identities read-only before any
new version probe. The post-settlement reader separately checks custody without
executing another child, including failed/timed-out installation; changed or
unavailable custody marks the observation partial without replacing native exit.
Opt-in execFile uses Buffer output, so its stream lengths/digests bind original
bytes; UTF-8 decoding is only for safe projection. Direct reader fixtures passing
strings are explicitly labeled UTF-8 representations, not original child bytes.
Invalid UTF-8 in native output remains partial evidence.

The successful synthetic case first receives the controlled loopback producer's
exact archive through the existing configured-npm registry receiver, with scripts
disabled, a private cache/config and a finite child budget. It then enrolls those
verified bytes in the original publisher's artifactReceiving path and requires
actual archive-to-installed comparison. These are real operations on a synthetic
fixture, not production package admission. The observer-loss case separately
proves native graph acceptance with empty artifactReceiving. Existing artifact
comparison regressions remain required and unchanged.

### Native qualification configuration custody

Before interpreting a native fixture's phase evidence, bind every claimed isolation input to the selected PNPM version's actual reader. Parser acceptance alone is not evidence that a setting controls that reader. PNPM 11.28.5 obtains YAML globals through `getConfigDir(process)` and `XDG_CONFIG_HOME/pnpm/config.yaml`; an accepted npm-style `globalconfig` value does not replace this source. Its authentication-file reader is `getNpmrcAuthFile`, using `PNPM_CONFIG_NPMRC_AUTH_FILE` (or the supported CLI field). The isolated observation fixture supplies an empty private YAML global and empty private auth file through those existing readers in its own serial Node test worker, then restores that worker's environment. It does not change user files or production configuration.

The separate native npm archive-receiving fixture uses npm's own `NPM_CONFIG_USERCONFIG`, `NPM_CONFIG_GLOBALCONFIG`, and `NPM_CONFIG_CACHE`, plus child-local `NPM_CONFIG_UPDATE_NOTIFIER=false`. These are npm inputs, not a claim about PNPM11's YAML global reader. Empty configuration does not replace the unchanged consumer workspace release-age policy, frozen lock, or script refusal.

Record the selected native source identity, fixture input hash, actual command/exit, and phase/receiving receipt for the first corrected assay. Keep an earlier rejected invocation as failed evidence. A source-reconstructed diagnostic whose digest matches the captured stream is identified as reconstructed, not retained raw output. No institutional Procedure identifier or successful receiving is created by this qualification procedure.

### Exact policy-attestation coverage and prepared selection

PNPM11.28.5's `resolvePublishedAt` can call `fetchAttestationPublishedAt` between
abbreviated and full metadata. The observer selects only the same registry's
`/-/npm/v1/attestations/<name>@<version>` for an already selected exact package,
classified as `attestation`. Existing normalized collision refusal and privacy
limits apply. A404 is observed response status and native fallback, not a valid
attestation or policy completion. Headers and body completion never prove
attestation authenticity, age acceptance or store commit. The native fixture
counts that exact route, returns404 and requires its observed headers; it neither
disables policy nor admits generic unknown requests. An earlier unclassified
count is preserved as unknown, not retroactively labeled as this request.

Each receipt records `preparedConfiguration` SHA256 and byte length over exact
prepared config bytes, committing selection and limits without emitting URLs.
It identifies the prepared snapshot; separate custody evidence qualifies whether
those bytes remain unchanged after settlement. A changed config does not acquire
the original digest's identity. Qualification compares unchanged saved bytes and
explicitly verifies the changed-config case retains a mismatching prepared hash.

Before original-consumer observation, select the native archive target from its
explicit lock tarball or the exact installed provider's native missing-tarball
derivation using effective registry/server type/name/version. Do not substitute a
metadata-advertised acquisition URL by assumption. This service observes selected
endpoints; it does not introduce another resolver or authenticate configuration
from a caller-supplied digest.
