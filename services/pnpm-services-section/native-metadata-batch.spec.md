# Bounded native metadata batches — owning component contract

Status: source-only extension of the received one-name PNPM metadata service; no batch native receiving, publication, installation or consumer adoption is implied. Owner: `@red-cup-engineering/pnpm-engineering-services-section`, original repository `red-cup-engineering/jsnode-packaging-engineering-services-section`, physical `services/pnpm-services-section`; base integrated PR5/main `d66f2ae3`. Existing native-metadata-preparation/session/transport/configuration contracts remain governing.

## Requirement, allocation and environmental expectations

The consumer must receive original native v12 metadata for a complete identified registry selection closure without manually performing one operation per name. Existing one-name receiving has demonstrated media0.2.0, HTTP0.6.2 (with structural0.6.3 coverage), and zod3.25.76 in one owned cache. The full795 selection records denote727 distinct names; this context is not itself a received closure. A bounded native batch amortizes supplier/context serialization and native startup while preserving the source/published/artifact/installed distinctions.

PNPM owns exact query projection, provider/config/transport custody, opaque ticket transitions and native result/file receiving. Existing npm composition owns original bounded synchronous execution and whole worker-group lifetime. The caller owns actual authorization, exclusive source/cache allocation, complete canonical selection provenance, fresh aggregate capacity and finite serial batch composition. The parent must remain alive; escaped descendants, crash-safe recovery, HTTP-body hard bounds and filesystem race isolation are not supplied. The service never imports an executor or receives callbacks/argv from operation JSON.

Native basis: qualified PNPM11.28.5 distribution SHA256 `e3738fda08262f74611d7a1ffc11b3e87fa52b466c07eb73211d179ebcb98810`, Node24.19.0. Native `outdated [<pkg> ...]` uses Promise.all for aliases; its registry gate initially permits Infinity, so networkConcurrency1 does NOT serialize metadata. Maximum4 distinct names bounds alias-resolution fan-out, not HTTP transactions, total response bytes, or age/trust effects. `fetchTimeout:15000` is native inactivity handling and `fetchRetries:0` does not eliminate semantic304/refetch. Native metadata saves are best-effort, nontransactional temp/rename writes. Failure can leave any subset; no rollback, cleanup, retry or accepted prefix is inferred.

## Interfaces and invariants

BATCH-1. `projectNativeMetadataBatchQuery(input)` shall accept an own-data record containing exactly `names,selections,policy,canonical,registry,directory,cacheDirectory`. Names shall be a dense nonempty unique array of1–4 normalized exact npm names admitted by the existing one-name grammar; order is retained. Each name shall occur in the complete original selections. This prevents wildcard/alias broadening and unbounded fan-out. Trace: finite batch scenario and native matcher behavior.

BATCH-2. The projector shall reuse the existing selected-version, SRI, registry, canonical digest, nonzero strict authored-policy and path validations. It shall retain the complete original selection array once, unchanged, including all versions of each name; it shall select the first original version per name as representative, without inventing policy or normalizing authored values. House-rule projection remains an independent explicit owner input. No exact-artifact ticket, source authenticity or age exception authority follows. Trace: canonical closure identity and current native metadata design.

BATCH-3. The projector shall generate one private manifest, one minimal wanted lock with one importer, one root-only packages[] policy and one registry configuration. Both dependency maps shall have exactly the batch names/representatives, and the command shall contain the existing fixed outdated controls followed by exactly those names. No scripts, packageManager/runtime, peer/dev/optional dependency categories, overrides, exotic references, recursive/global operation or installable graph shall appear. Unchanged fetch controls remain operational, not policy. Trace: exact native command and absence-profile compatibility.

BATCH-4. The projection shall identify kind `pnpm.native-metadata-batch-query.v1`, names, members[{name,representative,selectedVersions,expectedMirrorPath}], expectedMirrorPaths array, originalSelections, canonical/policy/registry/directory/cacheDirectory, fixed generated files/argv/provider, and a SHA256 binding the complete generated bytes, ordered names and original canonical context. Serialized projection remains within the existing8MiB bound. Neither name order nor dependency policy may be silently rewritten. Trace: immutable query/input identity.

BATCH-5. `receiveNativeMetadataBatchFiles(query,{maximumBytes}?)` shall rederive projection custody before IO and use the existing stable/no-follow regular-file receiver for every expected native mirror (maximum64MiB each, not an HTTP-write cap). It shall return one batch identity, `files:[{name,...originalMirror,selectedIntegrityCoverage:[{version,integrityMatches}]}]` and `allFilesObserved` boolean. Every file binds the same batch projection SHA256. Structural observations shall separately retain every selected version's manifest/timestamp coverage and exact selected-integrity string match, without making timestamp/SRI coverage a new policy gate. Each field `nativeReaderConsumed`, `strictPolicyVerified`, `installationReceived` remains false; native transition evidence belongs to the session. Trace: full set receiving versus raw diagnostic coverage.

BATCH-6. `createNativeMetadataBatchPreparationService()` shall share the existing metadata session implementation, source/provider/config/CA/transport custody and exclusive receipt writer. Its service/ticket/receipt kinds shall distinguish batch identity. The one-name factory, exports, kinds, result shape and acceptance semantics remain unchanged. No parallel transport implementation or executor/controller is introduced. Trace: architecture allocation and compatibility.

## State transitions and effects

BATCH-7. Batch prepare shall validate every own-data input before provider work, require the generated query directory and *all selected* mirror paths absent, bind original provider/source/CA bytes, create only the generated private query files and retained prepared receipt, then issue one process-local WeakMap ticket. Unrelated already-received cache names are allowed and not modified. A selected existing mirror refuses without deletion. One ticket stores complete context once. Trace: fresh producer distinction and same-cache composition.

BATCH-8. Batch state transitions shall be the existing prepared-producer→producer-in-flight→producer-received→reader-in-flight→complete sequence, with failed/unknown terminal variants, one request issuance per phase and busy guards. A copied/wrong-factory/replayed ticket or wrong phase refuses. Source/config/provider/CA/transport custody is rechecked before each issue and after each native result. Producer rechecks all absences. Reader rechecks every received mirror hash before issuing the same argv plus the sole offline flag. Trace: no replay and exact launch context.

BATCH-9. Result receiving shall require the existing exact JavascriptNode@1 receipt/request/result contract, original no-error/no-signal statuses0/1, complete bounded stdout/stderr and a JSON object with exactly the requested top-level names, each with the exact representative wanted string. Duplicate top-level JSON package keys, including escaped-equivalent names, shall refuse after ordinary JSON.parse syntax validation. The bounded top-level key scan is not a parallel generic JSON parser; nested fields retain native JSON serializer/JSON.parse semantics. Missing/extra names, arrays, wrong wanted or malformed output shall not advance. Original raw admissible executor receipt is retained before parsing/custody interpretation; the composing owner remains responsible for retaining original results that exceed the service's bound. Trace: native outputs are a complete matrix, not exit-code authority.

BATCH-10. Producer acceptance shall require every expected stable native mirror. Reader acceptance shall require every previously received mirror still present with unchanged bytes and the complete output matrix. Partial mirrors remain observed evidence only; any failed/unknown result blocks the reader or completion for the whole batch. Acceptance still means native offline metadata command/readability receiving, NOT native verification of every selected version, maturity/trust, archive identity, lock semantics or installed consumer. Native can report wanted even when no latestManifest exists under its age handling; raw coverage must remain distinct. Trace: complete batch receiving and native semantic limits.

BATCH-11. After a known unsuccessful or uncertain producer, the service shall retain raw/phase-prefix and observed file evidence, mark failed/unknown, and issue no reader/retry/cleanup. It shall not independently wait for, kill, or infer settlement of processes. Phase service receiving occurs inside the still-live original worker after the synchronous executor returns from the direct native child. The identified native cache writers belong to that direct PNPM process; its possible error-path ps descendant is read-only. FINAL parent acceptance occurs only after the existing composing supervisor has stopped and observed quiescence of the entire owned outer group, then revalidated source/query/mirror custody. Native requests/writes can overlap before the direct child returns, and Promise.all rejection does not cancel siblings. Recovery/adoption of failed-prefix mirrors requires a separately specified owner operation, not fresh-absence bypass. Trace: highest-risk partial native failure.

## Resource and composition limits

BATCH-12. Batch size is at most4 distinct exact names. Each existing phase remains45000ms/1048576-character service output allowance; the original sync mapping uses1MiB as a stop threshold, possibly overshooting by a native chunk, and the composing owner retains original evidence under its existing16MiB file cap before PNPM receiving. Projection8MiB, input/data-tree bounds, receipt16MiB and per-file post-read64MiB remain unchanged. These are local parsing/evidence limits, not end-to-end body/memory/cache reservations. Aggregate capacity and serial finite-batch admission belong to the caller. No unbounded batch/tranche loop or implicit extra command appears in this service.
